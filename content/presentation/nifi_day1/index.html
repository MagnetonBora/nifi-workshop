S5
Data in motion vs data at rest

Two different kinds of data work

Data at rest

  • Data sitting in storage: databases, data lakes, file systems.
  • Tools: SQL engines, Spark in batch mode.
  • Unit of work: a query or a job over a bounded data set.

Data in motion

  • Data moving between systems: events, logs, messages, CDC rows.
  • Unit of work: an event or a batch of events.
  • What matters: latency, ordering, delivery guarantees, back pressure, lineage.
Apache NiFi · Workshop
S6
Where NiFi fits

NiFi is a data movement tool

  • Dynamic routing and delivery of data between heterogeneous systems.
  • Receive, validate, transform, enrich, deliver, and keep the full provenance history.
  • Do light processing in NiFi: filtering, normalization, routing, format conversion.
  • Leave heavy aggregations and large-window joins to Spark, Flink, or a SQL engine.

Unit of processingTable / file / data setFlowFile (an event or a batch of events)
Key metricJob execution timeThroughput, latency, backlog
FailuresRe-run the jobRetry, back pressure, redelivery
TransparencyJob logsData Provenance for every FlowFile

S8
Flow Controller

The brain of the node

  • Flow Controller schedules processors, hands out threads from the pool, and manages queues and repositories.
  • A processor does not own a thread: the controller calls onTrigger on schedule.
  • Through a ProcessSession the processor takes FlowFiles from incoming queues and transfers them to outgoing ones.
  • 2.x: only the timer-driven thread pool remains; event-driven scheduling was removed in 2.0.
  • Bulletins: problem reports from components, shown as a red icon, on the Bulletin Board, and via the API.
Practical takeaway: before migrating, switch any components configured as Event Driven to Timer Driven. The removal is confirmed by distribution docs based on NiFi 2.0; Apache Migration Guidance has no separate line for it.

S11
Copy-on-write

Content is immutable

  • A written content claim is never modified: changing content means reading the old claim and writing a new one.
  • Cloning a FlowFile (fan-out to two relationships) copies only a reference, not the bytes.
  • Attribute-only operations (UpdateAttribute, RouteOnAttribute) are cheap: content is untouched.
  • Every content transformation is read + write I/O: long chains of content-rewriting processors load the disk.
  • Disk space is freed when no references remain; deleted content may stay in the archive for a while.
This is the main motivation for record-based processing with as few content-rewriting steps as possible.
Apache NiFi · Workshop
S12
FlowFile lifecycle

How a FlowFile moves through the repositories

  1. session.create() creates a FlowFile; session.write() puts content into a new claim.
  2. session.transfer() + commit(): WAL update, provenance events, then the FlowFile lands in the queue.
  3. A terminal processor or auto-terminated relationship produces a DROP event.
Apache NiFi · Workshop
S13
Delivery semantics

At-least-once inside a node

  • Processing is organized as session transactions: commit or rollback.
  • On rollback the FlowFile returns to the incoming queue (sometimes with penalization): no data loss between steps.
  • A failure after an external side effect but before commit leads to reprocessing.
  • Idempotent writes on the destination (Kafka, DB, REST) are the flow designer's responsibility.
Durability: by default nifi.flowfile.repository.always.sync=false and nifi.content.repository.always.sync=false. The OS flushes asynchronously, so an OS or power crash can lose the latest changes. true increases reliability at the cost of throughput. The checkpoint interval differs between docs (2 mins) and shipped configs (20 secs): check your own nifi.properties.
Apache NiFi · Workshop
S14
Swapping

FlowFiles in memory

  • FlowFile metadata (attributes) lives in the JVM heap.
  • To avoid OutOfMemory, NiFi swaps FlowFiles from queues to disk above nifi.queue.swap.threshold (default 20,000 per queue).
  • Millions of tiny FlowFiles hurt both heap and speed.
  • Prefer hundreds of large FlowFiles carrying batches of records (record-based processing, MergeRecord).
Rule of thumb: many records per FlowFile, not one record per FlowFile.

S25
Content-based routing

When attributes are not enough

  • RouteOnAttribute sees attributes only.
  • RouteOnContent: regular expressions over the content (scans the content).
  • QueryRecord / PartitionRecord: split by field values without Split processors.
  • EvaluateJsonPath / ExtractText: pull a value into an attribute first.
Extract into attributes only small values: attributes live in the heap and in the WAL.
Apache NiFi · Workshop
S26
Merging

Merging flows and data

  • Fan-in: several incoming connections to one processor are allowed.
  • MergeContent: byte-level merge (binary concatenation, TAR, ZIP, Avro).
  • MergeRecord: record-aware, schema-aware merge (full reference: Day 2, section 2.2.6).
  • Key settings: min/max entries (records), min/max group size, Max Bin Age, correlation attribute, merge strategy (Bin-Packing / Defragment).
Always set Max Bin Age so the tail of the data is not stuck waiting for a full bin.
Since 1.8 MergeRecord honors Minimum Number of Records: for large output files set the minimum close to the maximum.
Apache NiFi · Workshop
S27
Back pressure

Back pressure protects the system

  • Each connection has an Object Threshold and a Size Threshold: defaults 10,000 FlowFiles and 1 GB.
  • When either threshold is reached, the source processor stops being scheduled until the queue drains.
  • One full outgoing connection (often failure) stops the processor, even if other connections are empty.

Design practices

Naming and documentation

Naming

  • One standard: <Action> <Object> [<Source/Destination>].
  • Examples: Consume orders from Kafka, Validate order schema, Route invalid orders to DLQ.
  • Names must be clear without opening the configuration.
  • Name connections only when it adds meaning (valid, invalid).

Documentation

  • Use Comments on components and Labels on the canvas.
  • Describe the group contract: inputs, outputs, formats, SLA.
  • Fill in the Process Group description.
Apache NiFi · Workshop
S31
Design practices

Modularity and anti-patterns

Modularity

  • Process Group per function: ingest, validate, transform, deliver, error handling.
  • Groups talk through Input/Output Ports.
  • Parameter Context for every environment-specific value; inheritance base → prod.
  • Create Controller Services at Process Group level, not root, unless needed globally.

Anti-patterns

  • "Spaghetti" of hundreds of processors on one canvas.
  • Hard-coded URLs and passwords.
  • Large content fragments extracted into attributes.
  • Endless failure → same processor loops without a retry limit.
  • Unnamed processors.

S35
The record concept

Why one FlowFile per object does not scale

Classic model

  • A JSON array of 10,000 events → SplitJson → 10,000 FlowFiles.
  • 10,000 FlowFile Repository entries and provenance events.
  • 10,000 onTrigger calls on every step; heavy heap pressure.

Record-oriented model

  • A FlowFile is a set of records of one format.
  • Format (JSON, CSV, Avro, Parquet, XML…) is abstracted by Reader and Writer services.
  • Records are streamed: one record in memory at a time.
QueryRecord and MergeRecord have their own memory nuances: not every processor is purely streaming.
Apache NiFi · Workshop
S36
Reader → Processor → Writer

The record processing pipeline

  • Record Reader: JsonTreeReader, CSVReader, AvroReader, ParquetReader, XMLReader, GrokReader.
  • Record Writer: JsonRecordSetWriter, CSVRecordSetWriter, AvroRecordSetWriter, ParquetRecordSetWriter.
  • Schema describes fields and types; the Writer may use a different schema than the Reader.

S42
JsonTreeReader

Infer Schema and its limits

  • One Reader accepts a single object, an array of objects, and NDJSON.
  • Extra pass over the data to infer the schema: noticeable CPU/I/O on large FlowFiles.
  • Unstable schema between FlowFiles: 1, 2, 3 → integer, but 1.5 elsewhere → a different type; all-null fields get no useful type.
  • Silent propagation: a Writer with Inherit Record Schema repeats the "random" schema; errors surface only at the destination.
  • No contract: no required fields, date formats, decimal precision, or defaults.
  • Dates: 2026-11-15T10:00:00Z may stay a string or become a timestamp depending on Reader formats.
Apache NiFi · Workshop
S43
JsonTreeReader

What the JsonTreeReader reference confirms

  • Default Schema Access Strategy is Infer Schema: unless you change it, the Reader infers the schema from each FlowFile.
  • Accepts JSON-per-line (NDJSON), single objects, and arrays; array elements become separate records.
  • With an explicit schema, JSON fields missing from the schema are dropped, and schema fields missing from the JSON become null.
  • Infer Schema Cache: without it inference repeats for every FlowFile; with it a found schema is reused.
Consequence: with an explicit schema, everything needed downstream (Jolt, QueryRecord) must be described in the Reader schema. A schema cache is a cheap optimization, not a replacement for a schema contract.
Apache NiFi · Workshop

When to define the schema explicitly

  • Any production flow.
  • Writing to databases and columnar formats (Avro / Parquet).
  • Validation with ValidateRecord.
  • Data shared between several teams.

S45
Performance

Tuning Readers and Writers

  1. Explicit schema instead of Infer: no extra pass, stable types.
  2. Minimal transformations: no extra ConvertRecord for JSON → same JSON.
  3. Writer: Pretty Print JSON = false; Output Grouping: Array or One Line Per Object (NDJSON).
  4. Writer schema with the desired field order defines the output order.
  1. Binary formats (Avro, Parquet) are cheaper than JSON; convert at the boundaries.
  2. FlowFile size: aim for tens to hundreds of MB, not gigabytes.
  3. Concurrent Tasks scale record processors, but only with several FlowFiles in the queue.
  4. Reuse services: one Reader/Writer for many processors.
NDJSON is friendlier than arrays for Splunk, Kafka, and logs: it can be cut by lines, concatenated, and streamed.

S49
SplitText

SplitText: recommendations

  • Split in large batches (Line Split Count = thousands of lines), not line by line: this already half-solves the small-FlowFile problem.
  • Very many parts increase memory pressure (FlowFiles with attributes live in memory, not the content).
  • If needed, use two-stage splitting: large chunks first, then smaller ones.
  • SplitText does not understand JSON: it will cut pretty-printed multi-line JSON in the middle of an object.
For multi-line JSON use SplitRecord or SplitJson, not SplitText.

S53
QueryRecord

QueryRecord: SQL instead of Split → Evaluate → Route

  • Write a SQL query over the records of a FlowFile (the table is called FLOWFILE); the result becomes the output content.
  • Each dynamic property = one relationship: property name = relationship, value = SQL SELECT. At least one is required.
  • ANSI SQL on Apache Calcite; needs a Record Reader and a Record Writer.
Apache NiFi · Workshop
S54
QueryRecord

Three typical queries, three relationships

-- relationship "errors": only errors, only the needed fields
SELECT ts, svc, msg FROM FLOWFILE WHERE level = 'ERROR'

-- relationship "normal": everything except DEBUG
SELECT * FROM FLOWFILE WHERE level <> 'DEBUG'

-- relationship "stats": aggregate per service
SELECT svc, COUNT(*) AS cnt FROM FLOWFILE GROUP BY svc

S57
Lab 3 · Methodology

Lab 3: how to measure

  1. Same input: e.g. 100 FlowFiles × 100,000 records (GenerateRecord → Number of Records).
  2. Freeze conditions: empty queues, equal Concurrent Tasks.
  3. Run A; record time, Tasks/Time, Bytes Read/Written, queue counts, heap/GC, provenance events.
  4. Clear queues, run B on the same input, repeat the measurements.
  5. Repeat 3 times and take the median.
Expected: B is noticeably faster with less heap/GC pressure, and orders of magnitude fewer provenance events. Get the numbers in your environment.
Correctness: valid + rejected = input count; check record.count.
Pitfalls: table name must be FLOWFILE; decimal vs double → explicit schema; MergeContent waits → set Max Bin Age.

Configuration files

Practical rules for configuration changes

  1. Change configuration through configuration management (Ansible, Helm values, images), not by hand on nodes: nodes stay consistent.
  2. Restart where required (nifi.properties, bootstrap.conf); after a change check nifi-app.log for startup errors.
  3. Keep secrets (keystore passwords, nifi.sensitive.props.key) out of config repositories and logs; restrict file permissions (chmod 600/640, owned by the NiFi user).
  4. Copy a file before editing it; take a full backup of conf/ before a migration (Block 2.4 and 3.1.5).

S65
Coordination

Leader election, state, and flow election

  • Coordinator and Primary are chosen by leader election: Apache ZooKeeper by default; in 2.x also Kubernetes Leases / ConfigMaps.
  • In 2.6.0 the ZooKeeper integration moved into a separate NAR.
  • ZooKeeper is also the cluster state provider (e.g. List* pointers); local state lives in state/local.
  • Flow election: nodes vote for the flow, waiting for max.wait.time or max.candidates; the most-voted flow wins.
  • A node with a different flow syncs to the cluster flow after backing up its own.

S68
Load balancing

Balancing in practice and Offload

  • Load balancing costs extra network I/O and repository writes on the receiving node.
  • Do not enable it "just in case" on every connection.
  • Typical design: distribute once right after the source, then process locally.
  • 2.3.0 fixed distribution for partition by attribute; 2.10.0 fixed rare offload/balancing issues.
Offload before maintenance: the node stops accepting new data and hands its FlowFiles to other nodes. Cluster dialog → Disconnect → Offload, then stop the node safely.

S72
Configuration facts

What to remember about configuration

  • 2.x does not use flow.xml.gz: nifi.flow.configuration.file must point to flow.json.gz.
  • Previous flow versions are archived in conf/archive: your first line of configuration rollback.
  • nifi.sensitive.props.key encrypts sensitive properties: losing it means re-entering all sensitive values. Mandatory since 1.14.0.
  • JVM settings live in bootstrap.conf (java.arg.N); the default heap is small (~512 MB).
  • Default ports: HTTPS 8443, load balancing 6342; cluster protocol and Site-to-Site ports are configurable.
  • Put repositories on separate volumes: at least FlowFile apart from Content, and Provenance separately.

S74
Flow versioning

Version control workflow

  1. Process Group → Version → Start version control: choose client, bucket/branch, flow name.
  2. After changes the group shows locally modified: Show local changes displays the diff.
  3. Commit local changes creates a new version; Revert local changes rolls back.
  4. On another environment: Import from Registry or Change version; NiFi stops affected components and applies changes.
  5. Since 2.5.0 git clients can handle parameter values so environment-specific values are not committed.

Change management

Practices for safe changes

  • Environments dev → test → prod: the same flow version, only the Parameter Context differs.
  • Secrets only as sensitive parameters or Parameter Providers, never in Git.
  • Review changes in git (pull requests) instead of editing in the prod UI; restrict edit rights on prod.

  • XML Templates were removed in 2.0: use JSON flow definitions and versioning.
  • Since 2.1.0 the UI supports copy/paste of flow definitions between deployments.

S76
Stateless execution

Stateless Process Groups in 2.x

  • Since 2.0 any Process Group can run in Stateless mode.
  • The group runs as one transaction from source to sink, without persisting intermediate FlowFiles.
  • On failure the whole transaction is rolled back.
  • Gives exactly-once-like semantics for Kafka → … → Kafka chains.
  • Trade-off: limited parallelism and data sizes, because data is held in memory.
2.13.0 added in-memory content support for the Stateless engine (not available in 2.12.0).
