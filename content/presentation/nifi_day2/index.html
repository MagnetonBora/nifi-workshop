S8
JDBC driver · step 2

Place the driver on every node — outside lib/

Why not NIFI_HOME/lib

  • lib/ is the framework directory: third-party JARs can cause classpath conflicts.
  • Files in lib/ are lost or must be moved by hand on every upgrade.
  • A driver referenced by a service gets its own class loader — pools can use different driver versions.
nifi-node-1
$ sudo mkdir -p /opt/nifi/drivers/postgresql
$ sudo cp postgresql-<version>.jar \
      /opt/nifi/drivers/postgresql/
$ sudo chown -R nifi:nifi /opt/nifi/drivers
$ sudo chmod 750 /opt/nifi/drivers \
      /opt/nifi/drivers/postgresql
$ sudo chmod 640 /opt/nifi/drivers/postgresql/*.jar
# repeat on every cluster node (or roll out via Ansible / image)

DBCPConnectionPoolLookup

A pool vs a router of pools

  • DBCPConnectionPool — a real pool to one database: URL, driver, credentials, pool size.
  • DBCPConnectionPoolLookup — not a pool: per request it picks another DBCPService by the FlowFile attribute database.name.
  • Both implement DBCPService → selectable in the same Database Connection Pooling Service property.
  • Configured only via dynamic properties: key → target service. No EL, no sensitive values.
No database.name attribute, or a value that matches no key → exception when the connection is requested.

S14
DBCPConnectionPoolLookup

When to use a Lookup — and when not

Use it for

  • Multitenancy: a DB per customer, same schema, same flow — one flow instead of N copies.
  • Shards / regions: the same queries against several databases.
  • Read/write split: different keys for replica and primary branches.
  • Controlled switch-over between DB instances without editing processors.

Skip it when

  • There is only one database — a plain DBCPConnectionPool is simpler.
  • Databases need different SQL or logic — separate branches are clearer.
  • You need automatic failover — solve it in DNS or the DB cluster.

S16
DBCPConnectionPoolLookup

Pitfalls

  • The attribute name is fixed — database.name; the value must match the dynamic property name exactly (case-sensitive).
  • Security: if the value comes from external data (HTTP header, message field), it selects the target DB. Whitelist it with RouteOnAttribute.
  • Missing attribute / unknown key fails when the connection is requested — plan failure/DLQ branches and watch bulletins.
  • Enable targets before the Lookup; a target can't be disabled while the Lookup is enabled.
  • Cluster: the driver must be on every node; total connections = sum of pools × number of nodes.
  • Don't confuse it with DatabaseRecordLookupService / SimpleDatabaseLookupService — those enrich records for LookupRecord.

S19
Reading · pitfalls

Memory and SQL injection

Memory

  • Some JDBC drivers (PostgreSQL) load the whole result into client memory without cursor mode.
  • For Fetch Size to work, driver-specific settings may be needed (PostgreSQL: non-autocommit mode; exact conditions — pgjdbc docs on fetching results with a cursor).
  • Always bound queries by time or key.

Parameters in SQL

  • Substituting EL values into SQL text is vulnerable to SQL injection when values come from external data.
  • Use the parameterized path (sql.args.N.type/value with PutSQL).
  • Or validate values first (RouteOnAttribute / ValidateRecord).

S22
Writing · PutDatabaseRecord

Relationships and efficiency

Relationships

  • success
  • failure — the DB rejects the data (constraints, wrong types).
  • retry — transient issues (lost connection, deadlock).
Never loop retry back into the same processor without a limit.

Efficiency

  1. Large FlowFiles (thousands of records) + batch.
  2. Concurrent Tasks ≤ pool size; watch table locks.
  3. Idempotency for at-least-once: UPSERT / INSERT_IGNORE with a unique event key.
  4. Huge loads: DB bulk paths (COPY, bulk loaders) are outside NiFi.

Kafka · NiFi 2.x

A critical change: unified Kafka components

The "Kafka 2.6" processors — ConsumeKafka_2_6, ConsumeKafkaRecord_2_6, PublishKafka_2_6, PublishKafkaRecord_2_6 — were removed in 2.0.0.
  • Replaced by unified ConsumeKafka and PublishKafka plus the Kafka3ConnectionService Controller Service.
  • No separate Record variants: record mode is Processing Strategy = RECORD (consume) and the matching publish strategy.
  • Connection settings (brokers, TLS, SASL) are defined once in the service.
  • Processors don't depend on the client library version; one processor covers FlowFile / Record / Demarcator modes.

Kafka · batching

Batching and producer guarantees

  • Consume: one onTrigger reads a batch; with RECORD the batch becomes one FlowFile with N records — the key to throughput. Batch size = service property Max Poll Records (default 10000) plus Run Duration: larger → bigger batches, higher latency.
  • Publish: in RECORD mode each record is a message; the client batches them by linger.ms / batch.size.
  • Message size: don't publish megabyte FlowFiles as one message; watch broker message.max.bytes and client Max Request Size.
  • Producer side: critical flows — acks=all + idempotent producer; metrics/logs — weaker guarantees for throughput.
Sink idempotency is the main rule. At-least-once needs a unique event key + UPSERT, or DetectDuplicate, or deduplication in the sink.

Kafka · parallelism

One consumer per partition

  • Topic with 12 partitions, group nifi-orders.
  • 3 nodes × Concurrent Tasks = 4 → 12 consumers → 1 partition per thread (ideal).
  • Concurrent Tasks = 8 on 3 nodes → 24 threads for 12 partitions → 12 idle.
Rule: Concurrent Tasks × nodes ≤ partitions.

S37
Kafka · parallelism

Parallelism rules

  1. Concurrent Tasks × number of nodes ≤ number of partitions — more is useless.
  2. If ordering within a partition matters, avoid order-breaking steps after consume (Concurrent Tasks > 1 downstream, round-robin balancing).
  3. Rebalances pause consumption: don't restart ConsumeKafka needlessly; watch session/heartbeat timeouts.
  4. Few partitions but heavy processing → distribute after consume with Round robin load balancing on the connection.

NDJSON

Newline-delimited JSON (JSON Lines)

Every line is a standalone JSON object.
{"ts":"2026-11-15T10:00:00Z","level":"INFO","svc":"api","msg":"started","user":{"id":7,"pwd":"s3cret"}}
{"ts":"2026-11-15T10:00:01Z","level":"ERROR","svc":"api","msg":"db timeout","user":{"id":9,"pwd":"x"}}

Pros

  • Streaming without loading the whole array.
  • Easy split/merge by lines.
  • Great fit for Kafka, logs, and Splunk.

Cons

  • No common root element.
  • No line breaks inside an object (compact form only).

NDJSON in NiFi

Record pipeline for NDJSON

  • Writer: Output Grouping = One Line Per Object, Pretty Print JSON off.
  • Don't SplitText NDJSON per record — the Split anti-pattern. Bound batch size with SplitRecord (large Records Per Split) or MergeRecord.
  • MergeRecord: Bin-Packing Algorithm, Min/Max records, Max Bin Age (mandatory), optional Correlation Attribute.
  • Watch mime.type (application/x-ndjson or application/json) — HTTP delivery uses it as Content-Type.

Jolt · how it works

Walk the data tree and the spec tree together

Input-driven

  • shift: the engine walks the input and looks up a matching rule for each node.
  • Only what is explicitly matched reaches the output — everything else is dropped.

Spec-driven

  • default, remove, modify-*, cardinality: the engine walks the spec and applies rules to matching nodes.
  • default creates a node when it is missing.
The spec is a template with the same nesting as the data. Operations are combined in a chain: the output of one is the input of the next — Chain is NiFi's default.

Jolt · record flow

Jolt in a Record flow: what matters

  1. Input schema: the Reader builds records by its schema — fields outside an explicit schema are invisible to Jolt (JsonTreeReader docs confirm such JSON fields are skipped). Include every field the transform needs.
  2. Output schema: structure and types change after Jolt. Use a Writer that inherits the record schema, or — for deterministic order and types — an explicit Writer schema.
  3. Key order: decided by the Writer/schema, never by Jolt's output (see 2.2.4, ingest_ts first).
  4. Types: shift keeps value types; change types with modify-* and keep the Writer schema consistent.
  5. Errors: a bad spec or incompatible data → failure; the original goes to original only on success.

SQL nuances, cost and performance

SQL nuances

  • Reserved words (timestamp, user, value) or special characters → "double quotes".
  • Only fields in the Reader schema are visible; a field outside an explicit schema → failure.
  • Nested records/arrays work but get verbose — deep restructuring is Jolt's job.
  • Mind types: amount > '10' errors or surprises.

Cost

  • Each query is a separate pass and output (4 queries read the FlowFile 4 times, measured on 2.12.0) — split heavy queries.
  • Simple SELECT … WHERE streams; ORDER BY, GROUP BY, JOIN, window functions buffer in memory — bound FlowFile size first.
  • Result schemas are cached — uniform queries are faster.
  • Include Zero Record FlowFiles=false and explicit columns instead of SELECT *.

S97
Throughput

What drives Splunk delivery throughput

  1. FlowFile size and connections: one FlowFile with 10,000 events over a long-lived TCP connection is fast; 10,000 single-event FlowFiles + Connection Per FlowFile is very slow.
  2. Concurrent Tasks: each task holds its own connection; for ordered delivery use one.
  3. Send buffer and RTT: increase the buffer on high-latency links.
  4. Splunk-side parsing: LINE_BREAKER and timestamp lookup — a timestamp at the start of the object helps.
  5. Back pressure: a growing queue before PutSplunk is normal; tune thresholds and monitoring.
  6. TLS: CPU overhead on both sides.

Architecture choices

Acks, load distribution, and alternatives

  • Indexer ack (PutSplunkHTTP + QuerySplunkIndexingStatus): end-to-end confirmation at the cost of extra feedback loops and complexity.
  • Spread load across indexers: DNS round robin / L4 balancer, several PutSplunk to different indexers, load balancing on NiFi connections.

Decision checklist

How to choose — and the recommended path

  1. Queued data that can't be drained? → in-place.
  2. Must keep List*/QueryDatabaseTable* state? → in-place or planned reload with an idempotent sink.
  3. Many custom NARs and scripts? → fresh + rewrite.
  4. Repository encryption in use? → plan to exit it first.
  5. No downtime allowed? → parallel cluster.
  6. Not confident in testing? → fresh / parallel.

Production: blue/green

  • Test in shadow mode: separate consumer group in earliest, writing to test sinks.
  • Switch the real Group ID / sources; stop the old cluster but don't delete it until the observation period ends.
