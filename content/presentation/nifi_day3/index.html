S4
Design principles

Six rules for resilient flows

  • Handle every relationship: success goes on; failure / invalid / retry get their own path. Auto-terminate only deliberately.
  • Separate error types: transient (network, overloaded target) → retry; permanent (bad data) → dead-letter.
  • Isolate failure points: one slow target must not stop the others — separate Process Groups, queues, and back pressure.
  • Idempotency: NiFi is at-least-once; targets must tolerate repeats (UPSERT, event key, dedup).
  • Short transactions: split huge FlowFiles into reasonable batches so a retry does not reprocess gigabytes.
  • Observable errors: add error.stage, error.message, retry.count attributes for DLQ analysis.

S5
Failure and retry

Framework-level retry (since 1.16.0)

  • Any processor relationship can be marked as Retry in the processor dialog, Relationships tab.
  • Settings: Number of Retry Attempts, Backoff Policy (Penalize the FlowFile or Yield the processor), Maximum Backoff Period.
  • While attempts remain, the same processor reprocesses the FlowFile; afterwards it is routed to the relationship as usual.
  • Pro: no loops on the canvas. Con: a local decision on one processor without shared context.
  • For growing delays (exponential backoff): Backoff Policy + Maximum Backoff Period, or RetryFlowFile + UpdateAttribute computing the penalty.
Do not retry data errors (schema violations, HTTP 4xx, invalid) — send them straight to the DLQ. Authentication errors: alert the operator once attempts are exhausted.

S6
RetryFlowFile

Explicit retries with a dead-letter path

  • Counter attribute vs Maximum Retries: below the limit → retry (counter +1); above → retries_exceeded.
  • retries_exceeded goes to the DLQ — never back to the input, or the loop becomes infinite.

S8
RetryFlowFile · Pitfalls

What to watch out for

  1. The counter is never reset automatically. After a successful retry, a later RetryFlowFile with the same Retry Attribute keeps counting. Delete the attribute after success (UpdateAttribute → Delete Attributes Expression) or use a different attribute per retry point.
  2. Penalty (default 30 sec) protects the target from a retry storm: a penalized FlowFile is not picked up. If all FlowFiles in a queue are penalized, the UI shows it and the processor does not spin (since 1.16.0).
  3. Do not retry data errors (invalid, HTTP 4xx): retrying changes nothing.
The processor also writes <Retry Attribute>.uuid — the id of the processor that last retried the FlowFile.

S12
Dead-letter pattern

Typical DLQ implementation

...► ValidateRecord ─ valid ─► main flow
          │ invalid / failure
          ▼
   UpdateAttribute:
     error.stage   = validate
     error.time    = ${now():format(
        "yyyy-MM-dd'T'HH:mm:ss.SSSXXX")}
     error.reason  = ${validation.details:
        replaceNull('see bulletin')}
     original.name = ${filename}
          ▼
   PublishKafka (topic: dlq.<flow>)
     or PutFile /data/dlq/${error.stage}/
        ${now():format('yyyyMMdd')}/${uuid}

Good DLQ practice

  • Keep the original content unchanged plus error attributes (Kafka headers or a companion JSON).
  • validation.details is filled by ValidateRecord when Validation Details Attribute Name = validation.details.
  • Limit retention.
  • Have a replay flow that reads the DLQ and feeds data back once the cause is fixed.
  • Count with UpdateCounter and alert on DLQ growth.

S14
Restart · Stop sequence

What happens on nifi.sh stop

nifi.sh stop
  └─► Bootstrap sends the stop command to the JVM
        └─► Flow Controller stops scheduling processors (no new onTrigger)
              └─► waits for active threads up to nifi.flowcontroller.graceful.shutdown.period
                    ├─ finished → commit sessions → checkpoint FlowFile Repository → JVM exits
                    └─ not finished → threads terminated, open sessions rolled back
        └─► Bootstrap waits for the JVM up to graceful.shutdown.seconds (bootstrap.conf), then kills it
A rolled-back session puts the FlowFile back in its queue — the operation is repeated after start. Safe for idempotent sinks, a source of duplicates for the rest.

S18
Restart · Order

Stop from sources to sinks — start the other way round

  • No data is left with “nowhere to go”, and there is no burst of retries.
  • Stopping ConsumeKafka commits offsets and triggers a consumer-group rebalance — plan it.
  • Disabling Controller Services closes database and Kafka connections.
Apache NiFi · Workshop
S19
Restart · Runbook

Planned stop and planned start

Planned stop

  1. Announce maintenance; freeze flow changes.
  2. Stop sources: ConsumeKafka, Listen*, List*, QueryDatabaseTable*.
  3. Drain queues in data order; cap the wait at 5–15 min.
  4. Stop processors by group, then disable Controller Services.
  5. nifi.sh stop; confirm a clean stop in the logs.

Planned start

  1. Start NiFi; wait for UI/API and flow load.
  2. Check: no invalid/ghost components, services enabled, no bulletins.
  3. Start sinks → transforms → sources.
  4. Watch for 10–15 min: queues shrink, no back pressure, no error spike.
Failure/DLQ queues may stay on disk — they survive restart. Protect the sink from the backlog peak with ControlRate or temporarily lower Concurrent Tasks.

Restart · Automation

REST API instead of manual clicks

pg-control.sh
NIFI=https://nifi-1.example.com:8443/nifi-api
TOKEN=$(curl -s --cacert ca.pem -X POST "$NIFI/access/token" \
        -d "username=$NIFI_USER&password=$NIFI_PASS")   # lab only

PG_ID=<process-group-id>
# STOP all scheduled components of the group (use RUNNING to start)
curl -s --cacert ca.pem -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' \
     -X PUT "$NIFI/flow/process-groups/$PG_ID" \
     -d "{\"id\":\"$PG_ID\",\"state\":\"STOPPED\"}"
  • Every UI action is a /nifi-api call. Enable services with a similar PUT on /flow/process-groups/{id}/controller-services, body {"id":"<group id>","state":"ENABLED"}.
  • Paths /access/token, /flow/process-groups/{id}, …/controller-services, …/status are confirmed; check request bodies and responses for your version. Never keep passwords in scripts.

Wait for the stop, then use the NiFi CLI

wait-for-stop.sh
# wait until no processor threads are active in the group
until [ "$(curl -s --cacert ca.pem -H "Authorization: Bearer $TOKEN" \
      "$NIFI/flow/process-groups/$PG_ID/status" \
      | jq '[.. | .activeThreadCount? // empty] | add')" = "0" ]; do

done

S23
Restart · Supervisor

Kubernetes: StatefulSet, probes, disruption budget

  • StatefulSet with stable identities and persistent volumes for the repositories.
  • terminationGracePeriodSeconds longer than a clean stop; preStop can run the soft-stop script.
  • startupProbe with a large failureThreshold — otherwise kubelet kills a pod that is still loading.
  • livenessProbe not too aggressive (a GC pause must not restart the pod); readinessProbe: a TCP port check or /nifi-api/authentication/configuration — the only API endpoint that answers without a token (the rest return 401).
  • PodDisruptionBudget (at most one node down) and rolling updates one node at a time.
  • 2.x supports Kubernetes-based leader election without ZooKeeper.

Cluster operations

Rolling restart without downtime

  • Before: all nodes CONNECTED, ZooKeeper quorum, no invalid components, enough capacity without one node.
  • Offload needs load-balanceable connections; it is bounded by the graceful shutdown period.
  • Health check: node CONNECTED, no invalid components, balanced queues, no Kafka rebalance storm or lag.
  • Primary Node and Coordinator are re-elected; Primary Node Only processors move and read state from cluster state.

Self-healing · Design

Flow design that removes manual work

  1. Environment values live in Parameter Contexts.
  2. No loops without a counter — retry is always bounded.
  3. Every failure branch has a sink and an alert.
  4. Every external call has a timeout.
  1. Idempotent sinks — restarts and retries are safe.
  2. State lives in NiFi state, Kafka, or the sink — not in the operator’s head.
  3. Stop / start / clear / replay are written down as runbooks and automated.

Before the restart and after the start

Before a planned restart

  • Sources stopped; queues drained or consciously kept.
  • Controller Services disabled.

After the start (≈10–15 min)

Lab 8 · Flaky API

Simulate an unstable endpoint

flaky_api.py
import random
from http.server import BaseHTTPRequestHandler, HTTPServer


HOST = "0.0.0.0"
PORT = 9099


class RequestHandler(BaseHTTPRequestHandler):

    def do_POST(self):
        # Read the request body
        content_length = int(self.headers.get("Content-Length", 0))
        self.rfile.read(content_length)

        # Generate a random response status
        random_value = random.random()

        if random_value < 0.6:
            status_code = 200
        elif random_value < 0.9:
            status_code = 503
        else:
            status_code = 400

        # Send the response
        self.send_response(status_code)
        self.end_headers()
        self.wfile.write(b"{}")


if __name__ == "__main__":
    server = HTTPServer((HOST, PORT), RequestHandler)
    server.serve_forever()
503 is transient → retry. 400 is permanent → straight to the DLQ.

Lab 8 · Verification

What to check and what typically goes wrong

Verify

  • Most FlowFiles land in /data/ok; 400s and exhausted retries in /data/dlq.
  • Stop the flaky service: the queue grows, back pressure kicks in; after restart it drains without intervention.
  • Provenance: a retried FlowFile shows a chain of ROUTE / SEND events.

Pitfalls

  • Retry loop without a counter (no RetryFlowFile) → infinite retries.
  • A non-empty Failure queue blocks the source → route it to a sink.
  • The DLQ directory fills the disk → MonitorDiskUsage + cleanup.

S46
Site-to-Site Reporting

What Site-to-Site is

  • Built-in protocol for moving FlowFiles between NiFi instances (and from MiNiFi or client libraries).
  • The receiver exposes a Remote Input Port — an Input Port of the root group; the sender writes to it by name.
  • Transport Protocol: RAW (socket, default) or HTTP (works through proxies and load balancers).
  • Compression, batching, and distribution across the receiving cluster’s nodes.
  • The Destination URL is used only to establish the connection — data is balanced across all receiver nodes.
  • All three tasks ship in nifi-site-to-site-reporting-nar and exist in 2.x.
Apache NiFi · Workshop
S47
Site-to-Site Reporting

Architecture

  • Same NiFi as receiver: simple, but monitoring dies with the system.
  • Separate monitoring NiFi: recommended for production — alerts survive a main-cluster failure.
  • Several receivers: separate tasks per audience (e.g. security vs operations).

Performance and sizing

S68
Recovery strategies

Restart and failover

  • Processor / group: Stop → confirm no active threads → Start. Controller Service: Disable → Enable.
  • Node: graceful stop; after start check validity and queues — repositories recover from the WAL.
  • Failover: the cluster survives a node loss (with ZooKeeper quorum); Coordinator and Primary Node are re-elected; Primary Node Only processors start on the new primary.
  • Data on a failed node waits for it — unless storage can be attached to another node with the node identity, or data is re-read from sources (Kafka offsets commit after processing).
  • Disconnected node (since 1.16.0) can rejoin by syncing the flow (backing up its own).

JVM

Heap sizing in bootstrap.conf

# conf/bootstrap.conf
java.arg.2=-Xms8g
java.arg.3=-Xmx8g
# G1 is the default collector; change its options only after analysing GC logs
java.arg.N=-XX:+HeapDumpOnOutOfMemoryError

  • Heap is consumed by FlowFile metadata and queue entries, not content — it grows with the number of FlowFiles.
  • Leave RAM for the OS page cache (Content and Provenance repositories rely on it).
  • Enable GC logging; a bigger heap often masks too many FlowFiles.

S93
Threads

Thread pool and Concurrent Tasks

Maximum Timer Driven Thread Count

  • Shared pool for all components on a node: default 10 per node (3 nodes = 30 in total).
  • Start with 2–4 threads per core (community guideline, not a documented norm); if load average reaches the core count, reduce it.
  • Event-driven pool removed in 2.0.

Concurrent Tasks (per processor)

  • Threads one processor may use (default 1); raise for I/O- or CPU-bound steps with a queue.
  • Sum of active tasks ≤ the pool size.
  • Sources (ConsumeKafka, ListenX): ≈ number of partitions / channels.
  • Keep 1 for order-dependent or single-resource processors.

S94
Scheduling and cluster

Run Duration, scheduling, cluster parameters

  • Run Duration (0 ms … 2 s): several FlowFiles per session → fewer repository commits, higher throughput, but higher latency and more in flight on failure.
  • Run Schedule 0 sec = as often as possible; give sources a sensible interval. Penalty 30 sec, Yield 1 sec by default.
  • nifi.cluster.node.protocol.threads / .max.threads (default 50) for large clusters.
  • Load balancing: nifi.cluster.load.balance.connections.per.node (4), .max.thread.count (8), .comms.timeout (30 sec). More threads help only up to nodes × connections per node and add Content / FlowFile Repository writes.
  • ZooKeeper ensemble of 3 or 5, low latency; too aggressive heartbeat timeouts cause false disconnects during GC pauses.

Storage

How to choose and what to measure

  1. If possible, a separate volume for Provenance — even on NVMe (logical split, quota, own metrics).
  2. A single NVMe array is fine if you measure no WAL-latency degradation.
  3. Reduce provenance load: shorter retention, fewer indexed fields, tuned rollover. Don't disable it blindly — VolatileProvenanceRepository loses events on restart.
  4. Measure before / after: iostat -x (await, %util), fio, System Diagnostics.
  5. Spread Content across directories / devices; cap archive (max.retention.period, max.usage.percentage).
OS: ext4 / xfs with noatime; raise ulimit -n and process limits; plan enough inodes for many small claims.

S100
Flow design

Removing bottlenecks by design

  • Records instead of Split — the biggest win for CPU, heap, and repositories.
  • Fewer content rewrites: one QueryRecord / JoltTransformRecord instead of a ReplaceText chain.
  • No content in attributes (large EvaluateJsonPath / ExtractText).
  • Big output batches (MergeRecord) for DBs, Splunk, HTTP.
  • Parallelism only where narrow — at the slow step, not everywhere.
  • Avoid connection-per-FlowFile, Wait/Notify on hot paths.
  • Minimal complex regex on hot paths; prefer strict parsers.
  • Move "cold" paths (DLQ, audit) to separate groups.

S101
Throughput control

Prioritization and rate control

  • Prioritizers: NewestFlowFileFirst for fresh data; PriorityAttributePrioritizer for traffic classes.
  • ControlRate: limit by FlowFile count, size, or attribute value — protects targets.
  • Back pressure is the main regulator: object threshold protects heap, size threshold protects disk.
  • Load balancing evens out load — it is not a cure-all. Run Duration / Run Schedule balance latency vs throughput.
  • No hard QoS between Process Groups sharing one thread pool — for guarantees use a separate cluster / instance or cap concurrent tasks of less critical flows.
